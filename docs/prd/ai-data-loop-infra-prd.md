# AI Data Loop Infra PRD

## 目的

这份文档定义 `ai-data-loop-engine` 的**产品定位层**，用于回答一个比“当前仓库有哪些模块”更上层的问题：

> 我们到底想打造什么产品？它的核心边界是什么？为什么它不应该被定义为一个只服务自动驾驶的数据门户？

这份 PRD 的目标不是重写现有架构文档，而是为项目建立一个更稳定、更可迁移的产品心智模型：

- 它不是某个单一行业的专用工具集合
- 它不是只服务某个部门的数据门户
- 它也不只是本地 DataLake 的 demo workbench

更准确的定位是：

- **一套面向 AI 垂直场景、支持快速迁移的通用 AI Data Loop Infrastructure**

为避免概念混淆，本文默认使用统一六层模型来讨论系统底座：

1. 文件格式层：Parquet / Lance / Mcap / Lerobot
2. 存储层：local fs / S3 / MinIO / OSS / HDFS
3. 湖表格式层：Iceberg / Paimon / Hudi
4. 计算层：local Python / Dagster / Spark / Flink / Fluss
5. 查询层：DuckDB / Trino / StarRocks
6. 应用层：BI、挖掘检索、标注、需求管理、工作台等

其中元数据与事务控制层作为横切控制能力单独讨论，不简单并入上述任一业务层。

自动驾驶、机器人、座舱、多模态、视觉、语音等领域都可以成为它的落地场景，但都不应被固化为平台本体定义。

## 产品定位

### 一句话定义

`ai-data-loop-engine` 要打造的是：

- **可迁移、可编排、可治理的 AI Data Loop Infra**

它服务的不是某一个固定业务流程，而是所有需要把“原始数据 -> 数据资产 -> 数据集版本 -> 下游消费 -> 反馈回流”串起来的 AI 数据闭环场景。

### 产品本质

这个产品本质上是一套通用基础设施，而不是行业专用应用。

它需要同时承担以下角色：

1. **数据资产管理底座**
   - 管理原始数据、样本、标签、元数据、特征、索引、导出工件等对象
2. **数据流程编排底座**
   - 把 ingestion、清洗、转换、筛选、标注、索引、导出、交付等步骤编排起来
3. **数据任务执行与观测底座**
   - 统一承接长任务、异步任务、节点日志、状态监控、失败诊断
4. **数据版本与交付底座**
   - 支持 dataset version、artifact version、发布、冻结、导出与下游交付
5. **数据治理与追溯底座**
   - 支持 lineage、audit、quality gate、policy 与审批边界
6. **可迁移的领域解决方案底座**
   - 通过 schema、workflow template、adapter、profile 与 policy 快速适配不同 AI 垂直领域

如果映射到六层模型，这些角色大致对应：

- 存储层 / 湖表格式层 / 文件格式层：承接原始数据与结构化数据底座
- 计算层：承接 ingestion、转换、索引、导出、回流等流程执行
- 查询层：承接分析、过滤、交互式探索与服务侧读取
- 应用层：承接 BI、挖掘检索、标注、需求管理、运营工作台等角色入口

## 为什么不能把产品定义为“自动驾驶数据门户”

当前项目最早的落地语境确实与自动驾驶 / 机器人数据闭环紧密相关，这个背景没有问题。但如果把产品本体定义为：

- 自动驾驶数据门户
- 车端采集控制台
- 标注与采集运营系统总入口

会带来三个问题：

### 1. 过早把领域对象写死到平台主模型

例如：

- `Trip`
- `DriveSegment`
- 车型配比
- 实车 trigger
- 某种固定标注流程

这些对象可以是某个解决方案层的重要对象，但不应该一开始就成为平台主抽象。否则平台很难迁移到其他 AI 垂直领域。

### 2. 把“领域流程”误当成“平台能力”

真正可复用的是：

- 资产目录
- 元数据
- 任务系统
- 工作流编排
- 版本治理
- 质量规则
- 血缘追踪
- adapter/profile 机制

而不是某个行业特有的采集、回流或运营动作。

### 3. 会降低平台对外迁移与复用能力

如果产品表达始终围绕自动驾驶业务展开，那么：

- 机器人团队会觉得它“不像自己的平台”
- 多模态 / 语音 / AIGC 团队会难以映射到自己的问题域
- 平台能力很难沉淀为真正的 AI Data Infra

因此，自动驾驶应被定义为：

- **首个高复杂度验证场景**

而不是：

- **产品边界本身**

## 产品愿景

### 核心愿景

构建一套通用的 AI 数据闭环基础设施，让团队能够以统一方式处理以下问题：

- 如何把原始输入变成标准化的数据资产
- 如何把多个数据处理步骤编排为可复用的流程
- 如何管理数据集与版本演进
- 如何把数据交付到训练、评测、检索、分析、在线服务等不同消费面
- 如何让这些过程具备可追溯、可治理、可观测能力
- 如何让一个领域沉淀下来的能力，能够快速迁移到另一个 AI 垂直领域

### Modern Data Stack 一站式闭环愿景

我们把该项目定义为组织级 Modern Data Stack 的统一控制面，而不是“多个工具入口页”。

要解决的核心痛点：

1. 工具越买越多，集成复杂度持续上升，SDK/API/webhook 到处对接。
2. 元数据分散在不同工具，血缘、质量、告警、运行状态难以形成统一视图。
3. 运行与治理割裂，无法快速回答“谁在何时产出什么资产、失败影响什么下游”。
4. 成本与运维负担不断上升，变更与排障成本越来越高。
5. 组织被既有厂商生态与历史集成锁定，迁移和演进困难。

对应的产品目标：

1. 对初学者：提供开箱即用蓝图，快速跑通 ingestion -> materialization -> query/search -> export -> lineage。
2. 对企业：通过统一元数据、统一运行治理、统一上下文桥接，降低工具接入与迁移成本。
3. 对平台：保持 Vendor-Optional，任何工具都通过契约接入，不把平台主语义绑定到单一厂商。

该愿景在体验访问层的落地载体是 Tools 模块重构，目标不是替代 Dagster/Superset/Jupyter 等专用工具，而是在平台内形成统一工作空间、统一治理视图和统一跨工具上下文。

### 愿景边界

这个产品要做的是：

- 为不同 AI 场景提供共用数据基础设施

而不是：

- 亲自替代所有领域专用工具
- 在 v1 就覆盖完整 MLOps 全家桶
- 在核心层写死某个垂直行业的对象与流程

## 目标用户

平台的目标用户不应仅按“自动驾驶业务角色”划分，而应按通用 AI 数据基础设施中的稳定角色划分。

### 1. 数据生产者

负责把原始输入加工为可消费数据资产的人。

典型包括：

- 数据工程师
- 数据生产工程师
- 标注运营 / 数据运营
- 数据处理 pipeline 开发者

### 2. 数据消费者

负责使用数据资产进行模型训练、评测、分析、检索或产品优化的人。

典型包括：

- MLE
- 算法工程师
- 研究员
- 数据分析师
- 评测工程师

### 3. 流程设计者

负责定义数据处理流程、节点模板、规则模板和交付规范的人。

### 4. 平台管理员

负责权限、接入、治理、配置、审计、监控和平台运行的人。

### 5. 业务观察者

不一定参与底层流程搭建，但需要消费结果资产、报表、健康度与交付状态的人。

## 核心交付对象

平台交付的不是某一种行业专属产物，而是通用的数据闭环对象。

### 1. 数据资产

包括但不限于：

- raw asset
- sample
- label
- metadata
- feature
- embedding
- index
- report
- export artifact

### 2. 数据集与数据视图

包括但不限于：

- dataset

- candidate set

- training/evaluation/analysis consumption set

### 3. 流程结果

包括但不限于：

- task result
- workflow output
- quality report
- distribution report
- lineage record

### 4. 可复用平台能力

包括但不限于：

- workflow template
- node template
- schema template
- policy
- adapter
- runtime profile

## Core Platform Layer 与 Domain Solution Layer

这是产品设计里最重要的边界之一。

### Core Platform Layer

属于平台通用核心层，领域无关。

这一层负责：

- 身份与访问入口
- 资产目录与元数据
- 流程编排
- 任务执行
- 版本化与交付
- 质量治理
- 血缘追踪
- 观测审计
- adapter / connector / profile 扩展框架

### Domain Solution Layer

属于领域解决方案层，通过模板和适配器构建。

这一层负责：

- 领域 schema
- 领域 workflow template
- 领域 dashboard
- 领域 quality policy
- 领域 connectors
- 领域运营对象

例如：

- 自动驾驶方案
- 机器人方案
- 座舱方案
- 多模态方案
- 语音/NLP 方案

这些都应该建立在 Core Platform Layer 之上，而不是反过来污染 Core。

## 产品设计原则

### 1. Asset-centric，而不是 vertical-centric

平台围绕稳定的数据资产模型构建，而不是围绕某个行业对象构建。

优先抽象：

- asset
- dataset
- version
- artifact
- lineage
- task
- workflow
- quality rule
- policy

而不是优先抽象某个行业的专属语义。

### 2. Adapter / Profile 驱动演进

底层执行环境、存储、查询、索引、权限、调度能力都应通过 adapter/profile 机制演进，而不是通过重写产品主干演进。

### 3. Workflow-first，但不把流程写死

平台必须支持工作流编排，但流程节点与步骤应可配置、可模板化、可扩展，而不是内建固定行业流水线。

### 4. Domain schema 可扩展

平台核心对象应稳定，但允许领域在上层注入自己的 schema 与关系模型。

### 5. API-first / Control-plane-first

平台应优先提供稳定的 Platform API / control plane，而不是把能力锁死在某个 UI 界面里。

### 6. Local-first，但目标不是止步于本地

本地 MVP 是为了降低启动和验证门槛，不是为了把产品限定为本地工具。平台必须天然支持未来向团队版、企业版、SaaS 版迁移。

## 核心产品能力

### 1. 统一接入与工作台

平台需要提供统一的访问面，整合分散的数据工具、任务入口和资产视图。

包括：

- 统一身份认证
- 统一导航
- 统一搜索
- 统一工作台首页
- 统一任务与资产入口

### 2. 资产目录与元数据管理

平台需要提供统一的数据资产目录，管理各类资产的元数据、状态、归属和关系。

包括：

- 资产注册
- 资产浏览与搜索
- 标签与分类
- 元数据展示
- 生命周期状态管理
- 所属 workspace / project / domain 管理

### 3. 数据流程编排

平台需要支持把多个处理步骤编排成可执行流程。

通用节点类型包括：

- 数据导入
- 数据解析
- 数据清洗
- 数据转换
- 数据筛选
- 数据增强
- 标注调用
- 特征提取
- 索引构建
- 质量检查
- 数据发布
- 数据导出
- 外部系统调用
- 人工确认 / 审批

### 4. 任务执行与状态观测

平台需要统一承接流程执行、异步任务、节点状态与日志观测。

包括：

- 任务创建
- 调度与执行
- 状态跟踪
- 节点日志
- 指标监控
- 重试 / 取消
- 失败诊断入口

### 5. 数据版本化与交付

平台需要支持版本治理与多消费面交付。

支持的目标包括但不限于：

- 训练任务
- 评测任务
- 检索系统
- 分析系统
- 在线服务
- 外部平台

包括：

- dataset version 创建
- 版本比较
- 发布 / 冻结
- 导出
- 交付记录
- 消费记录

### 6. 数据质量与治理

平台需要支持质量检查、治理控制、审批与审计边界。

包括：

- quality rule
- quality check
- issue record
- publish gate
- audit log
- access policy
- sensitive data policy

### 7. 数据血缘与追溯

平台需要支持跨流程、跨资产、跨版本的血缘关系追踪。

包括：

- 输入资产 -> 流程 -> 输出资产
- dataset version 来源关系
- export / report / index 与源数据关系
- 用户操作审计

### 8. 工具与系统集成

平台不能假设所有能力都内建，而必须通过标准接口接入外部系统。

典型接入对象包括：

- 标注系统
- 数据处理引擎
- 计算平台
- 数据仓库 / 湖仓
- 检索引擎
- 实验平台
- BI 平台
- 工作流系统
- 权限系统

### 9. 领域模板与迁移机制

平台必须支持从一个 AI 垂直领域快速迁移到另一个领域。

这要求平台支持：

- schema template
- workflow template
- node template
- quality template
- dashboard template
- connector template

自动驾驶只是一个 template，机器人、多模态、语音、工业视觉等也都应能通过同样机制落地。

## 核心非功能需求与指标体系

这套 AI Data Loop Infra 不仅要定义功能边界，还必须定义可持续演进的非功能目标。非功能需求不是附属项，而是决定平台能否长期承接多领域迁移、持续交付与组织复用的核心约束。

### 三层指标结构

平台指标采用三层结构：

1. **业务交付层**
   - 关注保时、保量、保质、降本、提效、增值
   - 是结果导向指标，直接体现业务价值，通常对外可见
2. **系统能力层**
   - 关注稳定性、高可用性、可扩展性、可伸缩性、可观测性
   - 是技术导向指标，体现系统深度与工程体系化能力，通常对内可见
3. **组织与流程层**
   - 关注协作机制、流程标准化、知识沉淀与复用、工程效能与工具链成熟度
   - 是能力导向指标，体现团队持续成长与交付机制成熟度，通常作为内部建设指标

这三层之间不是并列关系，而是自下而上的支撑关系：

- 如果系统能力层具备高稳定性和高可用性，业务交付层才更容易做到保时、保质
- 如果系统能力层具备良好的可扩展性与可伸缩性，业务交付层才更容易实现提效与增值
- 如果组织与流程层的协作机制和流程标准化做得好，领域适配与平台推广会事半功倍，帮助业务交付层提效
- 如果组织与流程层的知识沉淀与复用做得好，新人 onboard 更高效，也更容易形成可迁移解决方案
- 如果组织与流程层的工程效能与工具链成熟度做得好，系统能力层也更容易做到长期稳定

### 指标设计原则

1. 指标必须可量化，不能停留在抽象目标层
2. 任一层级都可以承接阶段目标，但必须落到具体数值
3. 指标既要反映当前 MVP / P0 的现实约束，也要保留平台向团队版、企业版演进的衡量方式
4. 指标不应只关注系统本身，还应衡量平台是否真的降低迁移成本、提升交付效率与复用效率

### 业务交付层指标

业务交付层反映方案设计与执行成熟度，直接对业务结果负责。

#### 1. 保时
- 描述：是否满足单条数据或单次交付任务的时效要求
- Key Results：
  - KR1：单条数据端到端处理延迟控制在 **10 分钟级别**
  - KR2：标准数据集交付任务按期完成率 **≥ 95%**
  - KR3：高优先级交付请求的平均等待时间 **≤ 30 分钟**

#### 2. 保量
- 描述：是否满足平台面向生产任务的吞吐规模要求
- Key Results：
  - KR1：日均处理 clips / samples 数量达到 **100 万级**
  - KR2：核心批处理链路在峰值期间吞吐下降不超过 **10%**
  - KR3：标准导出任务日均成功交付量达到 **500+ 批次/天**

#### 3. 保质
- 描述：是否持续满足交付质量和问题控制目标
- Key Results：
  - KR1：每季度保证 **P0 质量问题 ≤ 1**
  - KR2：每季度保证 **P1 质量问题 ≤ 2**
  - KR3：核心数据集版本发布后的回滚率 **≤ 2%**

#### 4. 降本
- 描述：是否通过架构、流程和自动化降低综合成本
- Key Results：
  - KR1：平台化后综合云成本降低 **￥100 万/月**
  - KR2：冷数据与热数据分层存储后存储成本下降 **20%+**
  - KR3：重复开发和重复接入带来的隐性成本下降 **30%+**

#### 5. 提效
- 描述：是否显著提高人效与系统交付效率
- Key Results：
  - KR1：平台化后减少人力投入 **10 人天/月**
  - KR2：新建一条标准数据流程的配置与上线时间缩短 **50%**
  - KR3：同类资产交付的平均 lead time 缩短 **40%**

#### 6. 增值
- 描述：是否产生额外业务价值或长期复用价值
- Key Results：
  - KR1：完成至少 **3 个**跨领域可复用的数据流程模板沉淀
  - KR2：完成 sensor / topic / metadata 等异构数据对象的统一对齐能力
  - KR3：平台复用带来的新业务接入周期缩短到 **≤ 2 周**

### 系统能力层指标

系统能力层反映系统设计与技术架构深度，直接对可持续性与风险负责。

#### 1. 稳定性
- 描述：确保系统在各类运行场景下持续稳定，无重大中断或明显性能波动
- Key Results：
  - KR1：全年系统 **P0 / P1 级故障为 0**，P2 问题 **24 小时内恢复**
  - KR2：平均故障间隔时间（MTBF）**≥ 90 天**
  - KR3：重大回滚次数 **≤ 2 次/季度**

### 指标使用方式

这些指标不要求在同一阶段一次性全部达成，但每一阶段都应显式定义自己的指标目标，并且至少覆盖以下内容：

- 至少一个业务交付层指标
- 至少一个系统能力层指标
- 至少一个组织与流程层指标
- 至少一个可直接映射到 SLO / SLA / DORA 的工程指标

这样可以确保平台不会只追求功能堆叠，而忽略：

- 交付结果是否真实改善
- 系统能力是否真的可持续
- 团队机制是否支持平台长期演进
- 工程体系是否能够支撑持续发布、稳定运行和快速恢复

## 非目标

为了避免产品边界失真，需要明确以下内容不是当前产品本体目标。

### 1. 不是自动驾驶专用平台

自动驾驶可以是首个强验证场景，但不是产品唯一身份。

### 2. 不是单纯的数据门户聚合页

平台不只是把多个系统做 SSO + 导航拼接起来，而是要提供统一控制面、统一对象模型与统一执行面。

### 3. 不是单纯的标注系统替代品

标注只是 AI 数据闭环里的一个环节，不应主导平台整体定位。

### 4. 不是纯粹的 DataLake / Lakehouse 封装

底层存储与查询很重要，但平台还要处理任务、流程、版本、血缘、治理与交付。

### 5. 不是完整 MLOps 平台的直接替代

训练编排、模型注册、在线 serving 等能力可以通过接口集成，但不应让当前产品失焦。

## 自动化 / 自驱动 / 自进化 / 智能化的正确位置

这些方向仍然重要，但在产品中应作为**平台演进能力**，而不是绑定某个行业流程的内建特性。

### 自动化

平台支持基于规则、阈值、事件的自动化数据流程执行。

### 自驱动

平台支持基于依赖状态、资源状态和策略条件的主动流程推进。

### 自进化

平台支持基于数据规模、质量评估和效果反馈进行策略迭代和自动触发后续动作。

### 智能化

平台支持通过 Agent / 智能服务将领域专家经验沉淀为可复用能力。

这四类能力应以通用平台能力来表达，而不是默认绑定“车端 trigger”或“某类采集链路”。

## 首个落地场景与平台边界

### 首个落地场景

自动驾驶 / 机器人数据闭环是一个很好的首个验证场景，因为它天然具备：

- 多模态数据
- 高复杂度流程
- 标注 / 质检 / 导出链路
- 长任务与异步调度
- 版本治理和回流需求

这类场景非常适合验证平台的能力上限。

### 但这不等于平台本体

产品定义中必须始终坚持：

- 自动驾驶是 example
- 平台是 infra

领域对象、领域规则、领域 dashboard 应进入 Domain Solution Layer，而不是侵入 Core Platform Layer。

## MVP 范围建议

### P0：验证通用 infra 主链路

P0 的重点不是做完整行业应用，而是验证通用 AI Data Infra 的最小闭环。

建议优先覆盖：

1. 统一资产目录
2. ingestion -> materialization -> query/search/export 最小主链路
3. workflow / task 最小执行链路
4. dataset / version / export 最小治理链路
5. Platform API + BFF + Web workbench 最小访问面
6. adapter/profile 驱动的本地运行时装配

### P1：增强通用控制面能力

建议补齐：

1. 更强的异步任务与调度边界
2. 质量检查与治理基础层
3. 更丰富的 dataset version / artifact version 语义
4. query / analysis / notebook-facing access
5. 更明确的 connector / source registry

### P2：支持跨领域快速迁移

建议补齐：

1. 领域模板体系
2. 更强的 schema 扩展机制
3. 多租户 / 组织边界 / 权限模型
4. 企业化 provider 替换能力
5. Agent / intelligent service 扩展位

## 成功标准

如果这份产品定义是正确的，那么项目后续应当越来越清晰地体现以下结果：

### 1. 平台叙事不再依赖单一行业身份

用户读完文档后，会理解：

- 这是一套 AI Data Loop Infra
- 自动驾驶只是首个强验证场景

### 2. Core 与 Domain 的边界更清晰

后续新增能力时，团队会先判断：

- 这是 core capability？
- 还是 domain solution artifact？

### 3. 平台能力更易迁移

当团队尝试扩展到机器人、座舱、视觉、多模态等场景时，不需要推翻平台主干，而是主要扩展：

- schema
- workflow template
- adapter
- policy
- dashboard

### 4. 文档与代码演进更一致

产品定义层、架构层和实现层之间的边界会更稳定：

- PRD 定义产品边界
- architecture 定义技术边界
- code 实现这些边界

## 一句话总结

`ai-data-loop-engine` 的正确产品方向不是“继续强化某个行业专用数据门户”，而是：

- **把当前本地 MVP 演进为一套面向 AI 垂直领域、可快速迁移的通用 AI Data Loop Infrastructure**

自动驾驶可以继续作为首个复杂场景推动落地，但产品本体必须始终保持通用、可扩展、可迁移。
