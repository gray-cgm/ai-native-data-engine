# 读书笔记：从 DDIA 第一章看标注系统中的 OLTP/OLAP 与微服务划分

读完《Designing Data-Intensive Applications》第一章后，我对标注系统的架构有了更清晰的判断：**很多架构问题本质上不是“技术选型题”，而是“trade-off 题”**。最重要的两个问题是：

1. 对于标注系统而言，**事务处理和分析处理是否应该放在同一个系统里**
2. 对于数据闭环部当下，**是否还需要这几年衍生的众多微服务**

---

## 一、标注系统中的 OLTP 与 OLAP 应该分开看

DDIA 第一章明确区分了 **操作型系统 OLTP** 和 **分析型系统 OLAP**。\
两者面对的数据访问模式、服务对象、查询方式都不同。

### 1. OLTP 的特点

OLTP 更适合处理：

- 标注任务创建
- 样本领取
- 标注结果提交
- 任务状态更新
- 质检流转
- 用户权限校验

它的典型特点是：

- 查询通常是按 key 读取少量记录
- 写入是对单条记录的创建、更新、删除
- 延迟要求低
- 数据表示的是“当前状态”

这正是标注平台在线业务的核心。

### 2. OLAP 的特点

OLAP 更适合处理：

- 标注员工作量统计
- 标签分类分布统计
- 项目进度看板
- 返工率、通过率分析
- 时间趋势分析
- 跨项目聚合分析

它的典型特点是：

- 查询通常要扫描大量记录
- 关注 count、sum、avg 等聚合
- 支持复杂、临时、探索式分析
- 关注的是“历史过程”和“事件累积”

因此，**标注系统中的在线标注流程是 OLTP，统计分析看板是 OLAP**。

---

## 二、为什么不建议直接在 MongoDB 上同时做事务和分析

如果把 MongoDB 既作为标注系统的 transaction database，又直接在它上面跑大量统计分析，就会遇到典型的冲突。

### 1. 负载模式冲突

OLTP 需要大量低延迟的小读写，而 OLAP 需要扫描和聚合大量数据。\
一旦在同一个库上同时运行：

- 标注员提交标注会和统计查询竞争 CPU、内存、I/O
- 接口响应会变慢
- 高峰期可能影响在线业务稳定性

### 2. 数据组织方式不匹配

OLTP 更关注当前业务对象和当前状态，OLAP 更关注历史事件与聚合分析。\
标注业务文档结构即使适合事务处理，也未必适合直接做分析。

例如：

- 任务文档适合读写，不一定适合历史统计
- 嵌套结构适合业务建模，不一定适合多维聚合
- 当前状态适合展示，不一定适合分析趋势

### 3. “一套系统包打天下”通常不是最优解

DDIA 强调，随着工作负载变复杂，系统会越来越趋向专用化；**one size fits all 的时代已经过去**。\
因此，把一个系统同时承担：

- 在线事务
- 搜索
- 统计分析
- BI 报表

通常会越来越别扭。

## 三、MongoDB + CDC + Elasticsearch 的方案是否合理

如果把 MongoDB 作为 **system of record**，再通过 CDC 同步到 ES，在 ES 上做统计，这比直接在 MongoDB 上分析更合理，因为它符合“记录系统 + 派生系统”的思路。

### 1. 合理之处

这种方案的优点是：

- MongoDB 专注在线事务
- ES 承担查询视图和聚合统计
- 分析查询不会直接打到事务库
- 数据流边界更清晰

对于这些场景，ES 是可行的：

- 标注员工作量统计
- 标签分类计数
- 简单时间趋势
- 搜索 + 过滤 + 聚合的联合查询

### 2. 不足之处

但 ES 更擅长的是 **搜索与检索**，不是最理想的 OLAP 系统。\
如果统计需求变复杂，比如：

- 多维钻取
- 历史重算
- 审计型统计
- BI 报表体系
- 长周期趋势分析

那么 ES 可能逐渐不够合适。

所以更稳妥的理解是：

- **ES 适合搜索 + 轻量统计**
- **真正的分析系统应考虑 lakehouse / OLAP 引擎**

这也和项目当前强调的演进方向一致：\
先打通 `ingestion -> lakehouse -> platform` 闭环，本地版采用 `SQLite + Parquet + DuckDB + Lance` 的轻量组合。

## 四、从 DDIA 看，标注系统更合适的分层方式

一个更清晰的架构是：

- **MongoDB**：事务型主库，负责任务、标注、状态流转
- **CDC / 事件流**：把变更同步出去
- **ES**：搜索、过滤、轻量聚合
- **Lakehouse / DuckDB / ClickHouse 等**：更完整的分析统计

这种方式符合 DDIA 对 **system of record** 与 **derived data** 的划分：\
原始业务写入在操作型系统中完成，下游系统通过 ETL、CDC、流处理形成派生视图。

---

## 五、微服务首先是组织协作问题，不是纯技术先进性问题

DDIA 在讨论分布式系统时给出的一个很重要的启发是：**不要为了分布式而分布式，不要为了架构时髦而增加复杂性**。\
书里也强调，如果单机或更简单的系统足够，就不应该急于分布式化。

这让我更倾向于把微服务理解为：

> **微服务首先是解决“多人多团队协作”的办法，而不是默认更先进的技术架构**

微服务的优势在于：

- 职责边界清晰
- 团队可独立维护
- 服务可独立发布
- 不同模块可独立扩缩容

这在大团队、多系统、多业务域的情况下很有价值。

---

## 六、为什么在当前阶段不应过早微服务化

对中小团队、个人项目、早期产品而言，微服务也会带来明确代价。

### 1. 运维复杂度上升

每个服务都需要：

- 部署
- 监控
- 日志
- 告警
- 资源管理

这会明显提高工程成本。

### 2. 本地开发和测试更难

服务一多，就需要在本地同时启动多个依赖。\
接口调试、联调、测试环境准备都更复杂。

### 3. 数据一致性更难

DDIA 明确指出，当每个服务拥有自己的数据库后，跨服务数据一致性就不再由数据库保证，而变成了应用自己的问题。\
分布式事务通常并不是微服务中的主流解法，因为它削弱服务独立性，而且很多数据库也不支持。

这对标注系统尤其敏感，因为它常常涉及：

- 任务状态一致性
- 标注结果和质检结果一致性
- 用户、任务、项目之间的跨域数据关联

## 七、AI 时代下，微服务的收益可能下降

结合自己的理解，我越来越认同一个判断：

- 微服务的核心收益来自组织拆分
- 如果 AI 提升了个体工程能力，团队规模缩小
- 那么微服务带来的组织收益可能会下降
- 但它的分布式复杂性成本并不会自动消失

因此，在 AI 时代，很多系统未必需要默认采用重度微服务。\
更合理的方式可能是：

- **先做模块化单体**
- **先做清晰边界，而不是物理拆分**
- **当团队协作、规模、部署需求真的上来时，再拆服务**

这也符合本项目当前路径：\
先做 **local-first personal edition**，一台机器跑通闭环，再逐步演进到企业版和 SaaS 版。

---

## 八、结合本项目，对架构演进的理解

项目当前强调：

- local-first
- 一台机器可跑通
- ingestion -&gt; lakehouse -&gt; platform
- local-dev 使用 SQLite metadata + Parquet + DuckDB + Lance

这说明当前更适合的不是“先上很多微服务”，而是：

### 当前阶段

- 模块化单体或少量服务
- 尽量简化部署
- 先把主链路做通
- 先明确数据流和系统职责

### 后续阶段

随着团队规模、业务复杂度、租户隔离、权限控制、协作需求增加，再逐步演进到：

- 企业可复制版
- 多租户 SaaS 版

这比一开始就过度设计成微服务更符合 DDIA 的 trade-off 思维。

## 九、我的阶段性结论

### 关于 OLTP / OLAP

标注系统中的在线业务和统计分析本质上是两种不同工作负载，应尽量分开。\
MongoDB 可以做事务主库，但不宜长期直接承载复杂分析。\
更合理的做法是：

- MongoDB 做 OLTP
- ES 做搜索和轻量统计
- Lakehouse / OLAP 系统做更完整分析

### 关于微服务

微服务不是默认更高级，而是适合多团队协作的一种组织型架构。\
如果团队小、产品早期、系统尚处于本地 MVP 阶段，微服务往往会放大复杂性。\
因此更好的策略通常是：

- 先模块化
- 后服务化
- 按真实组织和业务复杂度演进，而不是按流行概念演进

---

## 十、一句话总结

**DDIA 第一章最重要的启发不是告诉我们“该用什么技术”，而是提醒我们：先看问题类型，再做架构权衡。**\
对于标注系统来说，这意味着：

- **不要把事务和分析混成一锅**
- **不要为了先进感而过早微服务化**
- **先用足够简单的架构跑通闭环，再按真实需求演进**
