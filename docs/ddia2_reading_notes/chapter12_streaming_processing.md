# chapter11_streaming_processing

> 流处理与自动驾驶Pipeline实践反思
> 

## 一、 核心概念：Batch vs. Streaming  
*   **边界与终点：** 批处理（Batch Processing）的输入是有界的，系统明确知道何时处理完毕；而流处理（Streaming Processing）面对的是随时间无限增长的增量数据，永远没有“处理完”的那一刻。  
*   **数据组织形式：** 在批处理（如文件系统）中，我们用“文件名”来标识一组相关记录；在流处理中，生产者（Producer/Publisher）生成事件，消费者（Consumer/Subscriber）处理事件，相关的事件通常被组织成 Topic 或 Stream。  
*   **状态与事件的哲学关系：** 状态变化的结果是事件流的积分，而事件流是状态变化的微分。流处理的本质是事件驱动架构。  

## 二、 消息传递与流的传输体系  
在发布/订阅模型中，系统设计没有银弹。面对“生产速度大于消费速度”时的系统背压（Backpressure）机制，我们需要拷问系统两个核心问题：  
1.  **流控（Flow Control）：** 当消费不过来时，系统是丢弃消息，还是阻塞生产者？  
2.  **堆积与存储：** 消息一直堆积会怎样？如果是基于内存（如传统RPC或某些UDP传输，虽快但不稳定），系统会OOM崩溃；如果写在磁盘（如Kafka等Message Brokers），磁盘的读写性能如何影响消息传递？磁盘写满又会引发什么雪崩？  

**反思与踩坑（1）：Kafka 消息堆积与重平衡**  
> 在几十个 Python Processor 组成的 Pipeline 中，常常遇到某个节点处理变慢（如算法推理,繁重CPU耗时任务），导致 Kafka 消息积压。如果消费时间过长，极易触发 Kafka Consumer 的 Rebalance，进而导致整个消费组停滞、消息进一步堆积。解决这类问题往往需要将长耗时任务隔离，或优化系统级的可观测性以便快速定位 K8s Pod 日志和 Kafka 积压情况。  

## 三、 流式分析（Stream Analytics）与时间窗口  
流处理早期多用于金融交易监控、制造业流水线监控。如今在AI和自动驾驶领域，海量数据流的生产与加工已经变成了新时代的“大型制造流水线”。  
过去的流处理设计往往只关注“搬运”，但实际上**流式分析（Stream Analytics）**才是挖掘数据价值的重点，包括：  
*   测量某类事件的发生频率（Rate）。  
*   计算时间周期内的滚动平均值（Rolling Average）。  
*   对比历史时间区间，检测异常趋势（Trends detection），如自动驾驶上百个dds topic json schema校验。  

**时间与窗口的挑战：**  
*   **时间域：** 到底是基于事件发生时间（Event Time）还是服务器处理时间（Processing Time）？严重滞后的“Straggler”消息是否还纳入统计？  
*   **窗口类型：** 翻滚窗口（Tumbling）、滑动窗口（Sliding）、跳跃窗口（Hopping）。  
*   **状态维护：** 窗口计算需要维护大量的中间状态，这对 Processor 的内存或本地磁盘能力提出了极高要求。  

## 四、 流处理中的 Join 操作与血泪教训  
DDIA 将流处理中的 Join 分为三种：  
1.  **Stream-stream join（窗口 Join）：** 维护多个事件流的状态并在时间窗口内匹配。  
2.  **Stream-table join（流表 Join）：** 事件流与数据库表进行 Join，用数据库信息丰富事件流。  
3.  **Table-table join：** 维护物化视图。  

**反思与踩坑（2）：Stream-Table Join 打爆外部系统**  
> 当 Kafka 流中的高并发消息直接去 Query 外部数据库（如 PolarDB）时，会瞬间耗尽数据库的连接数。最后的救火方案是依赖阿里云的连接池复用。  
> **DDIA 标准解法：** 对于 Stream-table join，流处理器通常需要将数据库表的数据（通过 CDC 变更数据捕获）作为本地状态（Local State）缓存在流处理器内存或本地磁盘中，通过 Hash Join 等方式在本地完成，而不是为每条消息发起一次昂贵的网络网络请求。  
> **宽带打爆问题：** 你提到复用 Stream Pipeline 跑 Batch 任务时将 OSS 带宽打满。这正是因为流处理系统往往为顺序追加写优化，而在遭遇历史数据“重跑（Backfill）”的高并发大吞吐时，如果不做精细化的流控（如并发度限制、降级机制），极易对下游存储系统造成 DDOS 攻击。  

## 五、 容错（Fault Tolerance）、一致性与状态恢复  
批处理失败只需丢弃文件重跑即可，但流处理永不停止，无法简单丢弃输出。  
*   **微批处理（Microbatching）与 Checkpoint：** 例如 Spark Streaming 采用微批回放，Flink 周期性生成状态检查点（Checkpoint）写入持久化存储。  
*   **精确一次（Exactly-once）与原子性：** 处理事件所产生的所有副作用（发消息、写数据库、状态更新）必须是原子的，要么全部成功，要么全部失败。  
*   **幂等性（Idempotence）：** 确保重跑结果依然一致，是流处理容错的核心底线。  

## 六、 自动驾驶 Pipeline 的架构反思与总结  
我经历过的pipeline，由二三十个 Python 脚本构成的基于 Kafka 的流式架构，在演进过程中必然面临以下结构性痛点：  

1.  **“烟囱式”开发的维护地狱：** 几十个独立的 Python 服务各自为战，工具间壁垒高，上下游新人接手需要读上千行老代码，极大地拉低了迭代速度。  
2.  **“看不见、跑不快”的黑盒效应：** 缺乏全局血缘和全链路可观测性。一条路采数据经过切分、脱敏、解析等多个 Topic 和算子，一旦中间丢数据，研发人员需要花费 30% 以上的时间在 Kafka 和 K8s 之间进行 Debug。  
3.  **流批一体与重跑的困境：** 数据闭环不仅需要流式的实时处理，还经常面临百万级 Corner Case 的历史数据回溯（Backfill）。用纯流式的框架去跑批处理，不仅容易打爆底层（如前述的 OSS 带宽问题），还需要极高的人工介入成本。  

**演进方向：**  
未来的自动驾驶数据底座，必然走向“控制面与执行面解耦”的平台化架构（如使用 Dagster、流批一体的弹性调度框架）。将通用的数据处理（JSON/Trajectory/点云解析）SDK化，让业务开发人员只需关注算子逻辑，而由调度中枢统一管理流控、背压、重试和数据校验，这才是走出“高级运维”泥潭的最终出路。
