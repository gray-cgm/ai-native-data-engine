# 读书笔记: DDIA2 Chapter 2

## 结合日常数据闭环平台工作的非功能需求

这章我读下来，核心不是“怎么把功能做出来”，而是：

> **一个系统，除了“能做事”，还要“持续稳定地做事、低成本地做事、可演进地做事”。**

所以非功能需求，不是“锦上添花”，而是平台能不能长期支撑业务的基本盘。

---

## 0. 指标

我比较认可用三层结构去看非功能需求。  
这 3 层不是并列关系，而是一个从下往上支撑、再从上往下反馈业务价值的完整链路。

- 如果**系统能力层**具备高稳定性和高可用性，**业务交付层**就能更好地保时、保质
- 如果**系统能力层**具备良好的可扩展性与可伸缩性，**业务交付层**更容易实现提效与增值
- 如果**组织与流程层**的协作机制和流程标准化做得好，适配工作能事半功倍，帮助业务交付层实现提效
- 如果**组织与流程层**的知识沉淀与复用做得好，新人 onboard 更高效，帮助业务交付层实现提效甚至增值
- 如果**组织与流程层**的工程效能与工具链成熟度做得好，系统能力层就能更容易实现稳定性

---

## 1. 三层结构

| 层级         | 指标类型                                                     | 指标特点                                     | 示例                                          |
| ------------ | ------------------------------------------------------------ | -------------------------------------------- | --------------------------------------------- |
| 业务交付层   | 保时、保量、保质、降本、提效、增值                           | 结果导向，体现业务价值，外部可见             | 按期交付、降低云成本、提升人效、带来新收入    |
| 系统能力层   | 稳定性、高可用性、可扩展性、可伸缩性、可观测性               | 技术导向，体现技术深度与体系化能力，内部可见 | MTBF、SLA、水平扩展设计、弹性伸缩、监控覆盖率 |
| 组织与流程层 | 协作机制、流程标准化、知识沉淀与复用、工程效能与工具链成熟度 | 能力导向，体现持续成长力，内部机制           | code review 流程完善度、CI/CD 自动化率        |

一个很重要的点：

> **目标可以对应任一层级，但必须带具体数值。**

没有数值，非功能需求就容易变成口号。

---

## 2. 业务交付层指标

这是方案设计与执行层面的成熟度，直接对业务目标负责。

| 指标类型 | 描述                         | 具体 Key Result 举例                            |
| -------- | ---------------------------- | ----------------------------------------------- |
| 保时     | 是否满足单条数据的延迟需求   | 单条数据端到端延迟在 10 分钟级别                |
| 保量     | 是否满足任务规模             | 每天处理的 clips 数量达到 100 万                |
| 保质     | 是否达到预期质量             | 每个季度保证 P0 质量问题 <= 1，P1 质量问题 <= 2 |
| 降本     | 是否优化了成本               | 降低成本 ￥100 万/月                            |
| 提效     | 是否提高了人效 / 系统效率    | 降低人力成本 10 人天/月                         |
| 增值     | 是否带来了额外收益或长期价值 | 实现了 sensor 和 topic 的对齐                   |

这一层最容易被业务感知，也是平台存在感最强的一层。

---

## 3. 系统能力层指标

这是系统设计与技术架构层面的深度，直接对可持续性和风险负责。

### 3.1 稳定性

目标是系统在各类运行场景下持续稳定，不出现重大中断或明显性能波动。

- KR1：全年系统未出现 P0 / P1 级故障，P2 问题在 24 小时内恢复
- KR2：平均故障间隔时间 MTBF >= 90 天
- KR3：重大回滚次数 <= 2 次/季度
- KR4：关键服务 CPU / 内存利用率波动范围维持在 ±10%
- KR5：在压测和真实高负载场景下，系统崩溃率低于 0.1%

### 3.2 高可用性

目标是系统就算出问题，也能尽量少中断、快恢复。

- KR1：全年系统可用性 Uptime >= 99.95%
- KR2：关键服务平均恢复时间 MTTR <= 30 分钟
- KR3：核心依赖 DB、缓存、消息队列具备多 AZ / 多集群容灾机制
- KR4：季度内通过 100% 的容灾演练，包含故障注入、流量切换
- KR5：系统重启、发布等计划性维护时间控制在 < 1% 的总运行时间

### 3.3 可扩展性

目标是架构可以随着业务增长平滑扩展。

- KR1：系统可无感知扩容到当前峰值负载的 2 倍
- KR2：单节点性能提升 30%，集群水平扩容线性效率 >= 80%
- KR3：支持模块化扩展，新增业务模块接入时间 <= 2 周
- KR4：数据库读写分离 / 分区后性能提升 >= 40%
- KR5：核心服务 QPS 峰值支持提升至现阶段的 2 倍

### 3.4 可伸缩性

可伸缩性和可扩展性不一样。  
前者强调**动态自动伸缩能力**，后者强调**架构是否支持扩展**。

- KR1：实现 CPU / 内存负载 > 70% 时自动扩容，< 30% 时自动缩容
- KR2：自动伸缩策略命中率 >= 90%
- KR3：高峰期资源利用率 >= 85%，低峰期成本下降 30%+
- KR4：扩容响应时间 <= 5 分钟
- KR5：实现 100% 无人工干预的资源调度流程

### 3.5 可观测性

目标是问题出现后，可以快速发现、快速定位、快速处理。

- KR1：所有核心服务日志覆盖率 >= 95%，埋点一致性通过自动校验
- KR2：监控告警误报率 <= 5%，漏报率 <= 1%
- KR3：平均问题定位时间 MTTD <= 10 分钟
- KR4：100% 服务接入统一的 tracing + metrics + logging 三位一体体系
- KR5：建立至少 10 个关键指标 dashboard，覆盖核心业务路径

## 4. 组织与流程层指标

这一层看的不是“项目做成了没”，而是：

> **团队有没有形成高效、可持续的产出机制。**

| 指标类型               | 描述                                       | 具体 Key Result 举例                                                     |
| ---------------------- | ------------------------------------------ | ------------------------------------------------------------------------ |
| 协作机制               | 团队成员之间、跨职能团队之间的沟通效率     | 会议效率评分 NPS、跨团队协作任务完成率、需求沟通轮次                     |
| 流程标准化             | 工作有没有标准流程和模板，是否减少个体依赖 | 关键流程文档化率、标准流程执行覆盖率、上线回溯报告输出率                 |
| 知识沉淀与复用         | 是否把经验转化为组织资产                   | 技术 / 方案文档数量或更新频率、内部知识库活跃度、新人 ramp-up 时间缩短率 |
| 工程效能与工具链成熟度 | 自动化、监控、测试、CI/CD 等支撑是否完善   | CI/CD 自动化覆盖率、测试覆盖率、平均部署周期、MTTR                       |

很多平台问题，最后都不是技术本身的问题，而是流程、协作和认知一致性的问题。

## 5. 结合 Chapter 2 的一些重点理解

### 5.1 响应时间、延迟、tail latency

平均延迟低，不代表用户体验就好。  
真正难的是 **tail latency**。

这些慢请求、慢处理往往是偶现的，而且受很多因素影响：

- 资源抖动
- 网络抖动
- GC
- 热点数据
- 锁竞争
- 下游依赖变慢

这类问题很难定位，所以更应该针对具体用户群体和业务场景制定 **SLO**。  
如果达不成，就会影响对外承诺，这就是 **SLA**。

我的理解是：

> **不要只看平均值，要看分位数，要看最关键路径上的尾延迟。**

---

### 5.2 failure 和 fault 的区别

这个概念很重要。

- **fault**：局部错误，组件级故障
- **failure**：已经发展成用户可见的系统级失效

可以简单理解成：

> **failure > fault**

所以设计重点不是追求系统里完全没有 fault，  
而是避免某个局部 fault 演变成系统级 failure。

这也是为什么要避免 **SPOF, single point of failure**。

---

### 5.3 容错不能只停留在设计图上

平台说自己有容错，不够。  
必须通过手段去验证：

- 容错实验，不通知随时删掉一些节点
- 压测
- 故障注入
- 错误处理演练
- 混沌工程 chaos engineering

只有真的练过，容错能力才算存在。

---

## 6. 硬件 fault 和软件 fault

### 6.1 硬件 fault

硬件出问题是正常现象，不是意外。

常见处理方式：

- 设备冗余
- 多机房 / 多 AZ
- 备份
- 自动切换

### 6.2 软件 fault

软件问题往往更难，因为软件是人写的，人本身就不稳定。

典型情况：

- 一个 bug 导致所有节点一起挂
- 一次错误配置导致服务整体故障
- 一个错误发布逐步把所有实例更新坏了

所以软件层面更依赖这些机制：

- 多节点容错
- 滚动更新
- 灰度发布
- 回滚
- 自动化测试
- 配置校验

一句话总结：

> **硬件故障更多靠冗余抗，软件故障更多靠工程体系抗。**

## 7. 可靠性和容错

我觉得这部分特别贴近实际工作。

人类设计和构建软件系统，运维系统的也是人。  
而人是不可预测的，也会犯错，甚至很多线上事故本身就是人为操作失误导致的。

比如：

- 配置改错
- 发布失误
- 手工操作误删
- 对系统认知不完整

所以提高可靠性，很多时候不是继续堆功能，而是尽量消除人的不确定性：

- 更多自动化测试
- 快速回滚机制
- 清晰的监控看板
- 更好的可观测工具
- 标准化的发布与变更流程

另外，对于容错性，要看组织优先级。  
很多公司在业务压力下，会优先交付功能性需求，非功能需求容易被延后。

所以我觉得组织层面应该提倡：

> **blameless postmortems**

也就是事故复盘不先追责，而是客观分析 incident 如何发生，再冷静找到系统性改进办法。

## 8. scalability，可扩展性

可扩展性不是一句“支持高并发”就结束了。  
前提是：**先了解当前系统负载**。

比如需要看：

- 吞吐量，每秒 / 每天请求量
- 每天新增数据字节数
- 数据库读写比例
- 缓存命中率
- 资源使用情况
  - CPU
  - 内存
  - 磁盘
  - IO
  - 网络带宽

然后定期根据增长预测，评估当前架构的极限：

- 瓶颈在哪
- 哪个模块最先撑不住
- 要在哪些维度上扩展
- 满足 SLA 的前提下，怎样把系统运行成本做到最低

这点很关键：

> **扩展不是越大越好，而是在满足目标的前提下，用合适的成本支撑增长。**

---

## 9. 几种常见扩展方式

### 9.1 共享内存

也可以理解为垂直扩展，靠更强的机器提升能力。

优点：

- 简单
- 协调成本低

问题：

- 有单机上限
- 成本可能越来越高
- 单点风险更集中

---

### 9.2 共享磁盘

多个节点挂同一个磁盘，比如 NAS、SAN。

问题在于需要解决锁和协调限制。
存算分离的数据库架构设计和它有点类似，只不过后者不是直接提供文件系统，而是提供一个更适合数据库的 API。

---

### 9.3 无共享架构

也就是水平扩展，最受欢迎。

优点：

- 可扩展性高
- 灵活性高

缺点：

- 需要显式分片
- 分布式复杂度会上来
- 数据分布、热点、重平衡都要处理

这也是为什么无共享架构虽然流行，但绝不是没有代价。

---

## 10. 提高可扩展性的一个经验

提高可扩展性的好办法之一当然是用微服务、模块化设计。  
但另外一个同样重要的经验是：

> **不要过度设计。**

很多时候，满足当下问题的简单方案就是最好的方案。

原因很现实：

- 复杂架构会带来额外认知成本
- 分布式系统会带来额外运维成本
- 过早设计大规模能力，可能最后根本用不上

所以平台建设要克制。  
不要为了“未来可能会有超大规模”就提前把系统搞得特别复杂。

---

## 11. 可维护性

对于遗留系统来说，维护往往比新开发更复杂。

我觉得可维护性主要看三件事：

### 11.1 可操作性

系统要容易运行、诊断、发布、回滚。

比如：

- 有好用的监控工具
- 告警可信
- 日志能查
- tracing 能串起来
- SRE 团队能高效支持

### 11.2 简单性

系统要对新用户、新研发友好，onboard 足够简单。

比如：

- 文档完整
- 模块边界清晰
- 本地开发环境容易搭建
- 核心链路容易理解

### 11.3 可演化性

系统未来接新需求时，改动成本不能太高。

也就是：

- 耦合不能太深
- 边界要清晰
- 变更影响面可控
- 允许逐步演进

一句话说：

> **一个系统维护成本高，很多时候不是因为它功能强，而是因为它难理解、难排障、难修改。**

---

## 12. 最后的总结

这章对我最大的启发是：

> **好系统不是永远不出错，而是出了错也不容易演变成业务灾难，并且可以以合理成本持续演进。**

如果把它映射到日常数据闭环平台，我会这样记：

- **业务交付层**看结果，保时、保量、保质、降本、提效、增值
- **系统能力层**看底盘，稳定性、高可用性、可扩展性、可伸缩性、可观测性
- **组织与流程层**看长期能力，协作机制、流程标准化、知识沉淀、工程效能

最后真正要做的，不只是把功能交付出来，而是建立一个：

- 出问题能扛住
- 流量涨了能扩
- 成本高了能收
- 复杂度上来了还能维护
- 新人进来还能快速接手

的系统和团队。
